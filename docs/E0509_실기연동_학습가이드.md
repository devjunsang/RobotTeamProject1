## 0. 한눈에 보기

```
 [Ubuntu 24.04 노트북 · ROS 2 Jazzy]                      [두산 컨트롤러 DRCF v2.10.3]        [손목 플랜지 X1]
                                                                                                     
  manual_controller (PyQt5 화면)                                                                        
     │  ROS 2 토픽/서비스 (/e0509_real/...)                                                              
     ▼                                                                                                 
  dsr_bringup2 ─ dsr_controller2 / dsr_hardware2 ──TCP 12345 (명령)──▶  DRCF  ──DRL 프로그램 실행──▶  RS-485
                                                 ──UDP 12347 (실시간)──▶         (flange_serial_*)      │
                                                                                                     ▼
                                                                         RH-P12-RN(A) 그리퍼 (Modbus RTU, 57600, ID 1)
```

- **팔**: ROS 2 서비스(`motion/move_joint`, `motion/move_line`) → 두산 드라이버 → 컨트롤러.
- **그리퍼**: PC에 직접 연결되어 있지 않다. PC가 짧은 **DRL 프로그램**을 컨트롤러에 보내면, 컨트롤러가 손목의 RS-485로 그리퍼에 **Modbus RTU** 명령을 보낸다. 결과는 컨트롤러의 범용 레지스터에 적어 두고 PC가 읽어 온다.
- **접속 관리**: 화면의 `접속 / 접속 끊기 / 재접속` 버튼이 `dsr_bringup2` 프로세스를 직접 켜고 끈다.

## 1. ARIS3에서 이 작업의 위치 — Task Manager인가?

**아니다.** ARIS3 설계(`ARIS3_상세설계_V0.2_전체아키텍처.html`, `aris3_task_manager/ROLE.txt`)의 Task Manager는
`TaskRequest → Validate → Plan(MoveIt) → Pick → Place` 를 순서대로 돌리는 **C++ 작업 상태 머신**(ROS 2 Action `/aris3/execute_task`)이다.
지금까지 만든 것은 그 **아래층**, 실제 장비와 직접 통신하는 부분이다.

| 만든 것 | 해당하는 ARIS3 모듈 | 설계 문서의 표현 |
|---|---|---|
| 그리퍼 열기/닫기/위치/힘풀기/상태 읽기 (`gripper_drl.py`, `robot_link.gripper_command`) | **aris3_control** | "Robot / Gripper Adapter — 그리퍼 명령 검증", "그리퍼 명령과 응답", PHASE 2 |
| 관절·좌표 한 칸 이동(jog), 상태 감시, 안전 검사 (`robot_link.py`) | **aris3_control** | "직접 관절 시험 · 상태 감시", "관절 목표값 유효성 검사" |
| 실제 로봇 접속/끊기/재접속 (`bringup.py`) | **aris3_bringup** | "시뮬레이션 / 실제 장비 구성 분리", "준비 상태 검증 후 기능 노드 실행" |
| 수동 조작 화면 (`gui.py`, PyQt5) | **aris3_gui** 의 시제품 | 로봇·그리퍼 상태, 작업 버튼, 로그 (설계는 C++ Qt) |
| 네트워크·드라이버·그리퍼 프로토콜 조사 결과 | **docs** | 오류 및 해결 과정 |

**Task Manager가 나중에 가져다 쓸 것**
- 그리퍼 동작 단위(`open / close / move(pos, 힘) / release / status`) → 설계의 `/aris3/gripper/command`(Action 또는 Service)로 감싸면 된다.
- "지금 움직여도 되는가" 판단(`why_not_ready()`: 연결·관절 데이터 신선도·STANDBY·동작 중 여부) → Validate 단계의 실제 장비 조건.
- 실패 처리 사례(그리퍼 무응답 → 재접속, 드라이버 비정상 종료 → 재시도) → Task Manager의 실패/타임아웃 처리 설계에 참고.

**언어 차이 주의**: ARIS3 설계는 control/task_manager를 **C++17(rclcpp)** 로 계획했지만 이 코드는 **Python(rclpy)** 이다. 실제 장비 검증용 도구로 쓰고, ARIS3 본 패키지로 옮길 때는 같은 절차를 C++로 다시 구현하거나, Python 노드를 서비스 경계 뒤에 두는 방식 중 팀이 정해야 한다.

## 2. 실제 장비에서 확인된 사실 (팀 공유용)

| 항목 | 값 | 비고 |
|---|---|---|
| 컨트롤러 IP / 포트 | `110.120.1.66` / 12345 (명령), 12347 (실시간 UDP) | 두산 기본값(192.168.137.100)이 아님 |
| PC 유선 IP | `110.120.1.x/24` 고정 | PC마다 다른 x. 이 문서 작성 PC는 `.50` |
| 컨트롤러 소프트웨어 | DRCF `GF02100300` = **v2.10.3** | 에뮬레이터(3.x)와 버전이 다름. 워크스페이스는 기본 `DRCF_VER=2` 빌드가 맞음 |
| 로봇 라벨 | E0509, 2023-09-22 제조 | 2024-04-11 이전 플랜지 배치: 5번 핀 24V 상시, 4/6번 RS-485 |
| 그리퍼 라벨 | `RH-P12-RN` (S/N SNPR24A020169) | 실제 펌웨어는 **(A) 버전**: 모델 번호 35074, 펌웨어 V15 |
| **그리퍼 통신 방식** | **Modbus RTU**, 57600 bps 8N1, ID 1 | DYNAMIXEL 2.0이 아님. DXL 패킷에는 응답하지 않음 |
| 그리퍼 위치 | 0 = 완전히 열림, 약 740 = 닫힘 | 최대 한계 1150. 화면은 740까지만 보냄 |
| 그리퍼 힘 | Goal Current (mA), 한계 661 mA | Goal Current가 0이면 움직이지 않음 |
| 그리퍼 전원 | 23.8 V | 접속을 끊으면 그리퍼 전원도 꺼지는 것으로 보임(아래 4장) |

**주의할 점**
- 접속하면 두산 드라이버가 **펜던트 제어 권한을 가져오고, 서보를 켜고, 자동 모드로 바꾼다.** 로봇에는 한 번에 한 PC만 접속한다.
- 이 화면의 정지 버튼은 **비상정지 버튼을 대신하지 않는다.**
- 실제 로봇에서 **그리퍼 손가락 동작**과 **이 화면으로 팔 이동**은 아직 시험하지 않았다(에뮬레이터에서만 팔 이동 시험).

## 3. 기술별 설명과 공부할 것

각 항목은 **무엇인가 → 이 코드의 어디에 쓰였나 → 꼭 이해할 점 → 공부 방법 → 스스로 점검** 순서다.

### 3.1 리눅스 네트워크 기초
- **무엇**: IP 주소, 서브넷(`/24`), 라우팅 표, ARP, 링크(케이블 신호) 상태.
- **어디에**: 로봇 연결 문제를 찾을 때 (코드보다는 장비 준비 단계).
- **꼭 이해할 점**
  - `ip route get <IP>` 로 패킷이 **어느 랜카드로 나가는지** 확인한다. 유선이 끊겨 있으면 `110.120.x.x` 같은 공인 IP 대역은 Wi-Fi를 타고 **인터넷으로** 나간다. 실제로 엉뚱한 해외 장비가 ping에 응답해서 로봇이 보이는 것처럼 착각할 뻔했다(응답 시간 66 ms, TTL 104 → 로컬 장비가 아니라는 신호).
  - 랜카드 상태 `NO-CARRIER`, `ethtool`의 `Link detected: no` 는 **케이블/물리 문제**다. IP 설정을 아무리 바꿔도 해결되지 않는다.
  - ARP `INCOMPLETE` = 같은 대역 장비의 MAC 주소를 못 받음 = 물리적으로 연결이 안 됨.
- **공부**: `ip addr`, `ip route`, `ip neigh`, `nmcli`, `ethtool`, `ping`, `traceroute` 직접 쳐 보기.
- **점검**: "ping은 되는데 12345 포트 연결이 거부된다"는 무엇을 의미하나?

### 3.2 ROS 2 핵심 개념
- **무엇**: 노드, 토픽(계속 흐르는 데이터), 서비스(요청-응답), 액션(오래 걸리는 작업 + 진행 상황 + 취소), 네임스페이스, launch, 패키지.
- **어디에**
  - 토픽: `/e0509_real/joint_states` 구독 (`robot_link.py`의 `_on_js`)
  - 서비스: `motion/move_joint`, `motion/move_line`, `motion/move_stop`, `system/get_robot_state`, `drl/drl_start` 등 (`robot_link.py`의 `__init__`)
  - 네임스페이스: 실제 로봇은 항상 `/e0509_real`, 시뮬레이션은 `/dsr01` → 시뮬레이션용 스크립트가 실제 로봇을 움직이는 사고를 이름으로 막는다.
  - 패키지 구조: `package.xml`, `setup.py`(`entry_points`의 `manual_controller`), `launch/real.launch.py`
- **꼭 이해할 점**: 서비스는 "명령 접수"까지만 답한다. 로봇이 **다 움직였는지는 따로 확인**해야 한다(이 코드는 로봇 상태와 관절 값이 멈췄는지로 판단 — `_run_motion`).
- **공부**: ROS 2 Jazzy 공식 튜토리얼 "Beginner: CLI tools", "Beginner: Client libraries"(Python), `ros2 topic/service/node list`, `ros2 service call`.
- **점검**: Task Manager가 서비스가 아니라 **액션**을 쓰는 이유는?

### 3.3 rclpy 비동기 호출과 스레드
- **무엇**: ROS 콜백은 executor가 돌린다. GUI는 Qt 메인 스레드가 돌린다. 둘을 섞을 때 막히지(deadlock) 않게 하는 방법.
- **어디에**
  - `start_link()`: 노드를 `MultiThreadedExecutor`로 **별도 스레드**에서 돌림.
  - `_call()`: `call_async()` + `threading.Event`로 작업 스레드에서 결과를 기다림. 콜백 스레드 안에서 결과를 기다리면 멈출 수 있어서 이렇게 했다.
  - `_poll_state()`: 끊긴 서버로 보낸 요청은 **영원히 답이 안 온다** → 2초 지나면 포기하도록 고침(재접속 후 상태가 안 바뀌던 버그의 원인).
  - 그리퍼·팔 명령은 작업 스레드에서 실행하고, 화면은 `QTimer`로 0.1초마다 값을 읽어 그린다.
- **꼭 이해할 점**: 화면 스레드에서 오래 걸리는 일을 하면 화면이 얼어 정지 버튼도 안 눌린다.
- **공부**: rclpy executors/callback groups 문서, Python `threading`(Lock, Event).
- **점검**: `busy` 플래그를 팔 이동과 그리퍼 명령이 **같이** 쓰는 이유는?

### 3.4 두산 ROS 2 드라이버 (doosan-robot2, jazzy)
- **무엇**: `dsr_bringup2`(실행), `dsr_controller2`(두산 API를 ROS 서비스로 노출), `dsr_hardware2`(ros2_control 하드웨어 인터페이스, 컨트롤러와 TCP/UDP 통신), `dsr_msgs2`(메시지/서비스 정의).
- **어디에**: `bringup.py`가 실행하는 명령
  `ros2 launch dsr_bringup2 dsr_bringup2_rviz.launch.py mode:=real host:=110.120.1.66 port:=12345 model:=e0509 name:=e0509_real remap_tf:=true gui:=false`
- **꼭 이해할 점**
  - `mode:=virtual`이면 Docker 에뮬레이터, `mode:=real`이면 실제 컨트롤러.
  - 접속 시 `dsr_hardware2`가 하는 일: 제어 권한 가져오기 → 서보 켜기(SAFE_OFF→STANDBY) → 자동 모드. **팔은 움직이지 않지만 장비 상태가 바뀐다.**
  - 이동 서비스 요청 필드: `mode`(0=절대, 1=상대), `sync_type`(0=끝날 때까지 기다림, 1=비동기). 이 코드는 **절대 목표 + 비동기**: 매번 현재 위치를 새로 읽어 작은 값만 더하고, 움직이는 중에도 정지 명령이 들어가게 한다.
  - 정지 종류 `stop_mode`: 0=STO(서보 전원까지 차단), 1=Quick(서보 유지 감속 정지). 이 코드는 1을 쓴다.
  - 컨트롤러 버전: 실제 로봇 v2.10.3. 두산 MoveIt bringup은 2.12 이상을 요구한다는 점을 Task Manager(MoveIt) 단계에서 고려해야 한다.
- **공부**: `doosan-robot2` README, `dsr_msgs2/srv/` 폴더의 `.srv` 파일 직접 읽기, 두산 매뉴얼의 movej/movel/stop 설명.
- **점검**: `sync_type=0`(동기)으로 바꾸면 정지 버튼에 어떤 문제가 생기나?

### 3.5 로봇 상태와 안전 개념
- **무엇**: 두산 로봇 상태(`INITIALIZING, STANDBY, MOVING, SAFE_OFF, SAFE_STOP, EMERGENCY_STOP, ...`), 서보 ON/OFF, 브레이크, 제어 권한.
- **어디에**: `robot_link.py`의 `STATE_NAMES`, `why_not_ready()`, `bringup.py`의 접속 완료 판단(STANDBY + 관절 데이터 수신).
- **꼭 이해할 점**
  - SAFE_OFF = 서보 꺼짐(브레이크가 팔을 잡음). 첫 접속 때 원격 서보 켜기가 10번 거부된 적이 있다(원인 미확인, 재접속에서 성공) → 반복되면 펜던트 쪽 알람/비상정지부터 확인한다.
  - 로그의 `level 1` 메시지는 **정보**(SYSINFO)다. DRL 실행마다 나오는 `1/1/2007`은 에러가 아니다.
- **공부**: 두산 사용자 매뉴얼의 로봇 상태/안전 설정 장, ISO 10218·협동로봇 안전 개념 개요.
- **점검**: "화면의 정지 버튼"과 "비상정지 버튼"은 무엇이 다른가?

### 3.6 ros2_control (ARIS3 PHASE 1과 연결)
- **무엇**: `controller_manager` + 하드웨어 인터페이스 + 컨트롤러(`joint_state_broadcaster`, trajectory controller).
- **어디에**: 두산 bringup 내부(`ros2_control_node`). 접속 로그의 "Could not enable FIFO RT scheduling" 경고는 실시간 우선순위 권한이 없다는 뜻이며 동작에는 지장 없었다.
- **꼭 이해할 점**: ARIS3 설계의 "자동 경로(MoveIt→trajectory controller)와 직접 관절 시험 경로를 분리하라"는 원칙. 이 수동 화면은 **두산 서비스(직접 경로)** 를 쓰므로, MoveIt 자동 실행과 **동시에 쓰면 안 된다.**
- **공부**: control.ros.org 문서의 "Getting started", `ros2 control list_controllers`.

### 3.7 DRL (Doosan Robot Language)
- **무엇**: 두산 컨트롤러 안에서 실행되는 파이썬 비슷한 스크립트 언어. 펜던트(Task Writer의 Custom Code)나 ROS `drl/drl_start` 서비스로 실행한다. **둘 다 같은 실행기**를 쓴다.
- **어디에**: `gripper_drl.py`가 그리퍼 명령마다 DRL 소스 문자열을 만든다(`build()`). 펜던트용 점검 코드: `drl/rh_p12_comm_test.drl.py`.
- **꼭 이해할 점**
  - 쓴 함수: `flange_serial_open/write/read/close`, `wait`, `set_output_register_int`, `tp_log`, `tp_popup`.
  - **DRL은 ROS에 값을 돌려주지 못한다.** 결과를 받는 방법은 두 가지다.
    1. **범용 출력 레지스터**(이 코드의 방식): DRL이 `set_output_register_int`로 쓰고 ROS가 `plc/get_output_register_int`로 읽는다. 이 컨트롤러에서는 **하위 1바이트만** 전달되고 값이 `<< 24` 된 채 돌아왔다 → 레지스터 하나에 1바이트씩 담는다(`reg_byte()`). 이전 실행 결과를 잘못 읽지 않도록 **실행 번호(token)** 를 마지막에 쓴다.
    2. **TCP 소켓**(팀 스크립트 `scripts/aris3_gripper_probe*.py`의 방식): DRL이 `client_socket_open`으로 노트북의 TCP 서버에 접속해 받은 바이트를 그대로 보낸다. 바이트 제한이 없어 진단에 유리하다.
  - 펜던트 실행은 `tp_log`/`tp_popup`으로 결과가 화면에 바로 보여서 원인 찾기가 쉽다.
- **공부**: 두산 프로그래밍 매뉴얼(DRL) — flange serial, register, socket, wait 함수. 파이썬 기초 문법이면 읽을 수 있다.
- **점검**: 같은 DRL 코드를 ROS에서 실행할 때와 펜던트에서 실행할 때 무엇이 같고 무엇이 다른가?

### 3.8 시리얼 통신: UART와 RS-485
- **무엇**: 비트를 한 줄로 보내는 통신. `57600 8N1` = 초당 57600비트, 데이터 8비트, 패리티 없음, 정지비트 1.
- **꼭 이해할 점**
  - RS-485는 두 선(A/B)의 **전압 차이**로 신호를 보내고, 송신·수신이 한 쌍의 선을 나눠 쓰는 **반이중**이며, 여러 장치를 한 줄에 매단다(ID로 구분). A/B가 뒤바뀌면 아무 응답도 없다.
  - 통신 속도가 다르면 상대는 쓰레기 바이트만 받는다 → 응답 없음.
  - 두산 손목 시리얼은 "pseudo flange serial"이다. 버퍼 255바이트, 내부 지연이 있다. 매뉴얼은 Modbus 같은 요청-응답 방식을 권장한다.
  - 여러 속도로 시험 패킷을 보낸 뒤 손목 시리얼이 응답하지 않는 상태가 됐고, **재접속하자 풀렸다.** 정확한 원인은 미확인이다. 그래서 **57600만 쓴다.**
- **공부**: "UART 프레임", "RS-485 differential half duplex termination" 검색, 오실로스코프/USB-RS485 변환기로 직접 패킷 보기.

### 3.9 DYNAMIXEL Protocol 2.0과 Modbus RTU
- **무엇**: 바이트 묶음(패킷)의 약속. 같은 RS-485 선 위에서 다른 언어다.
- **실제 바이트로 보기**

  DYNAMIXEL 2.0 브로드캐스트 PING (그리퍼는 무응답 — Modbus 모드라서)
  ```
  FF FF FD 00 | FE | 03 00 | 01 | 31 42
  헤더         ID   길이    명령  CRC
  ```
  Modbus RTU "레지스터 0을 1개 읽기"와 실제 응답
  ```
  요청  01 | 03 | 00 00 | 00 01 | 84 0A          (장치 1, 기능 03 읽기, 시작 0, 개수 1, CRC)
  응답  01 | 03 | 02 | 89 02 | 5E 15             (장치 1, 기능 03, 2바이트, 값 0x8902 = 35074 → RH-P12-RN(A), CRC)
  ```
- **꼭 이해할 점**
  - Modbus 기능 코드: 03 읽기, 06 레지스터 1개 쓰기, 16 여러 개 쓰기. 응답이 `기능코드 | 0x80` 이면 예외(에러) 응답이다.
  - 주소: 매뉴얼의 `40001` = 프로토콜상 레지스터 **0**. 레지스터 하나는 2바이트(큰 자리 먼저). 4바이트 값(목표 위치 등)은 레지스터 2개를 쓰며, 이 그리퍼는 **아래 워드가 먼저**다(읽은 현재 위치: 40291=701, 40292=0).
  - 한 레지스터에 1바이트 항목 두 개가 들어 있기도 하다(예: 40257 = 하위 Torque Enable + 상위 LED Red).
  - ROBOTIS의 공식 ROS 2 패키지(`ROBOTIS-GIT/RH-P12-RN-A`)는 **PC USB(U2D2), `/dev/ttyUSB0`, 4 Mbps, DYNAMIXEL 2.0** 을 가정한다 → 손목에 꽂힌 Modbus 모드 그리퍼에는 그대로 못 쓴다. 저장소의 `scripts/aris3_gripper_probe*.py`도 DYNAMIXEL 패킷이라 현재 설정에서는 응답이 없다(바꾸려면 Modbus 요청으로).
- **공부**: ROBOTIS e-Manual "DYNAMIXEL Protocol 2.0", Modbus 기본(“Modbus RTU frame”, “function code 03/06/16”) 자료, 위 바이트를 손으로 해석해 보기.

### 3.10 그리퍼 Control Table (RH-P12-RN(A))
- **무엇**: 그리퍼 안의 설정·상태 값 표. **EEPROM**(전원 꺼도 유지: ID, 통신 속도, 통신 방식 등)과 **RAM**(전원 켤 때마다 초기화: 토크, 목표 위치/전류 등).
- **어디에**: `gripper_drl.py` 맨 위 주석의 Modbus 주소 표.

  | 항목 | Modbus 주소 | 이 코드에서 |
  |---|---|---|
  | Torque Enable | 40257 하위 바이트 | 1 = 힘 들어감, 0 = 힘 풀림 |
  | Goal Current | 40276 | 잡는 힘(mA). 화면: 150/300/500 |
  | Profile Velocity | 40281–82 | 손가락 속도(0.01 rpm 단위, 0 = 프로파일 없이 최대 속도) |
  | Goal Position | 40283–84 | 0~740 |
  | Moving | 40286 하위 | 1 = 움직이는 중 |
  | Present Current / Position | 40288 / 40291–92 | 상태 표시 |
  | Input Voltage / Temperature | 40297 / 40298 | 0.1 V 단위 / ℃ |
- **꼭 이해할 점**
  - 동작 모드 5 = **전류 기반 위치 제어**: 목표 위치로 가되 힘은 Goal Current로 제한된다 → 물체를 잡으면 그 자리에서 정해진 힘으로 멈춘다.
  - 이동 명령 순서: 전류 → 속도 → 위치 → 토크 켜기 (`build('move')`). 토크가 꺼진 상태에서 위치를 써도 움직이지 않는다 → 이 성질로 손가락을 움직이지 않고 쓰기 기능을 실기 검증했다(`prepare` 명령).
  - 토크가 켜져 있으면 EEPROM은 잠긴다.
- **공부**: ROBOTIS e-Manual RH-P12-RN(A) 페이지의 Control Table 전체.

### 3.11 CRC (오류 검출 코드)
- **무엇**: 패킷이 깨졌는지 확인하는 2바이트 값.
- **꼭 이해할 점**: DYNAMIXEL과 Modbus는 **CRC 계산법이 다르다**(DXL: 다항식 0x8005, 상위 비트부터 / Modbus: 0xA001 반사형, 0xFFFF에서 시작). `gripper_drl.py`의 `crc16()`이 Modbus 방식이다.
- **실제 활용**: 처음 응답을 받았을 때 바이트 일부(`02`, `5E`)만 읽혔는데, 예상 응답 `01 03 02 89 02 5E 15`의 CRC 바이트와 정확히 일치해서 "그리퍼가 Modbus로 응답했다"고 판정할 수 있었다.
- **공부**: CRC-16 원리 글 하나 읽고, 파이썬으로 위 예시 CRC를 직접 계산해 보기.

### 3.12 PyQt5 화면 구조
- **무엇**: 위젯(버튼·라벨), 레이아웃(Grid/HBox/VBox), 시그널-슬롯(`clicked.connect`), `QTimer`, `QMessageBox`.
- **어디에**: `gui.py` — `_joint_panel`, `_cart_panel`, `_gripper_panel`, `_conn_buttons`, 0.1초마다 `_refresh`.

  - 화면은 값을 "그리기만" 한다. 안전 판단은 `robot_link.py`에 있다(화면 없이도 같은 검사가 적용).

### 3.13 리눅스 프로세스 관리
- **무엇**: 프로그램이 다른 프로그램을 켜고 끄는 법.
- **어디에**: `bringup.py`
  - `subprocess.Popen(..., start_new_session=True)`: bringup을 **자기만의 프로세스 그룹**으로 실행 → `os.killpg(pid, SIGINT)`로 launch 전체를 Ctrl-C처럼 끈다.
  - 끄는 순서: SIGINT → (20초) SIGTERM → (5초) SIGKILL.
  - `/proc/<pid>/cmdline`을 읽어 다른 곳에서 띄운 `ros2 launch dsr_bringup2 ... name:=e0509_real`도 찾는다.
  - `/proc/<pid>/status`의 `SigIgn`: 스크립트에서 `&`로 띄운 프로그램은 **SIGINT를 무시**한다 → 그럴 땐 바로 SIGTERM.
  - 검토했다가 뺀 것: `PR_SET_PDEATHSIG`(부모가 죽으면 자식에게 신호)는 부모 **스레드**가 끝날 때 신호가 가는 방식이라, 작업 스레드에서 실행하면 접속이 끝난 직후 bringup이 꺼질 수 있다. 대신 화면을 닫을 때 직접 끈다.
- **공부**: 리눅스 시그널(SIGINT/SIGTERM/SIGKILL), 프로세스 그룹과 세션, `ps -ef --forest`, `pgrep -af`.
- **점검**: `pkill -f '패턴'`을 셸 명령 안에서 쓸 때 그 셸 자신이 죽을 수 있는 이유는?

6. **움직이지 않고 쓰기 검증**: 토크를 끈 채 목표값을 쓰고 다시 읽어 일치 확인.
7. **장비 기록 남기기**: 버전, 설정, 실패 로그 줄 그대로.

| 첫 접속에서 서보 켜기 10회 거부 | 로봇이 SAFE_OFF에서 원격 서보 켜기를 거부(로봇 쪽 조건, 원인 미확인) | 몇 분 뒤 재접속에서 성공. 반복되면 펜던트의 알람/비상정지부터 확인 |
| 그리퍼 무응답 | 그리퍼가 **Modbus 모드**인데 DYNAMIXEL로 불렀음 | Modbus로 요청 → 응답 |
| 여러 속도 시험 후 그리퍼 계속 무응답 | 손목 시리얼이 멈춘 상태(원인 미확정) | 재접속으로 해결, 57600만 사용 |
| 레지스터 값이 이상하게 큼 | 이 컨트롤러는 하위 1바이트만, `<<24`로 돌려줌 | 레지스터당 1바이트 + 실행 번호 |
| DRL 실행마다 "로봇 에러 1/1/2007" | 정보 메시지(level 1) | 에러 칸에 표시하지 않음 |
| 재접속 후 화면 상태가 안 바뀜 | 끊긴 서버로 보낸 요청이 영원히 대기 | 2초 후 포기 |
| 2초 만에 재접속하면 드라이버 비정상 종료 | 컨트롤러가 이전 실시간(UDP) 연결을 아직 정리 중 → `dsr_hardware2`가 연결 실패 처리 중 double free | 끊은 뒤 최소 10초 대기 + 비정상 종료 시 1회 자동 재시도 |
| 백그라운드 bringup이 Ctrl-C로 안 꺼짐 | `&`로 띄운 프로세스는 SIGINT 무시 | `SigIgn` 확인 후 SIGTERM |
| 재접속 후 그리퍼 설정이 초기값, 온도 하락 | 접속을 끊으면 그리퍼 전원도 꺼지는 것으로 보임(직접 측정은 안 함) | 끊기 전 물건 내려놓기 경고, 접속 후 2초 대기 |

## 6. 공부 로드맵과 체크리스트

**1단계 — 장비와 연결 (반나절)**
- [ ] 노트북 유선 IP를 직접 설정하고 `ip route get 110.120.1.66` 결과를 설명할 수 있다.
- [ ] `ros2 launch dsr_bringup2 ... mode:=real`을 실행하고 SAFE_OFF→STANDBY 로그를 찾을 수 있다.
- [ ] `ros2 service list | grep e0509_real`에서 이동·DRL·레지스터 서비스를 찾을 수 있다.

**2단계 — ROS 2와 두산 서비스 (1일)**
- [ ] `ros2 service call`로 `system/get_robot_state`를 호출해 본다.
- [ ] `move_joint` 요청 필드(pos, vel, acc, mode, sync_type)의 의미를 설명할 수 있다.

## 7. 아직 확인하지 않은 것 / 열린 질문

- 실제 로봇에서 **그리퍼 손가락 동작**(열기·닫기·잡기 힘)과 동작 시간.
- 이 화면으로 **실제 팔 이동**, 그리고 그리퍼 DRL 실행 직후 팔 이동이 바로 되는지.
- 접속을 끊을 때 **그리퍼 전원이 정말 꺼지는지**(측정 필요). 꺼진다면 잡은 물체를 놓치는 시점.
- 손목 시리얼이 멈췄던 정확한 원인(여러 속도 중 어느 것 때문인지).
- 그리퍼를 DYNAMIXEL 2.0 모드로 바꾸는 것이 나은지(같은 그리퍼를 쓰는 다른 팀 설정과 맞춰야 함 — 바꾸지 않았다).
- ARIS3 본 패키지(C++)로 옮길 범위와 방식.
